# Live report request lifecycle

Official Puppeteer guidance confirms that, on request-based Cloud Run hosting, CPU is disabled after the response is sent. Launching Puppeteer after replying can take 1–5 minutes. The published application’s report `generate` procedure currently replies immediately and runs `runGenerationJob` with `void`, including browser PDF work after that response. This is a concrete hosting/code mismatch and a strong explanation for the observed production-only 30-second browser-start timeout. The timeout alone is not a measurement of CPU allocation or memory; those remain possible additional factors.

The development preview has a different resource and lifecycle environment. A successful image-build browser smoke test proves libraries and executable usability during the build, not that a detached live request has continuing CPU. The correct fix is to retain active requests while doing work, persist generated report sections before printing, and print through a separate awaited request so a failed PDF can be retried without rerunning the language model. The exact approved HTML typography and pagination must remain unchanged.

Reference: https://pptr.dev/troubleshooting — “Running Puppeteer on Google Cloud Run”. Managed deployment guidance specifies a 180-second request limit, 512 MiB instance memory and CPU guaranteed only during requests. These constrain the implementation: avoid detaching jobs, keep PDF work separate from report authoring, and avoid concurrent browser processes in one instance. Extending a launch timeout alone is not a sufficient repair.

## Implemented correction

The final-report authoring procedure now awaits its work before returning and saves the exact authored JSON in `pdf_pending` state. It does not launch a browser. The report workspace immediately follows with a separate, awaited counsellor-only PDF rebuild request. A refreshed workspace can finish a pending source once; a failed print offers Retry PDF rather than automatically rerunning authoring or looping browser retries. A prior released PDF stays stored until the replacement passes validation, but the counsellor screen does not present that older PDF as the pending replacement.

The master renderer now reuses one connected Chromium per server instance, rejects overlapping report operations, and uses a private browser context for each report. Pipe transport avoids relying on a WebSocket endpoint printed to stdout. A real-browser test showed that the old `--single-process` switch crashes private contexts; it was replaced with `--renderer-process-limit=1`, and both the real master-template test and the image smoke test now use the corrected setup. Browser reuse does not guarantee that all reports fit the live memory envelope; actual production success must still be checked.

The approved report HTML, typography, layout, narrative extraction and continuation-page logic were not changed. Validation includes the real browser/private-context smoke check, 48 focused tests (including mounted UI retry and stale-download checks), and the fictional end-to-end two-request report run, which passed all 19 simulation checks. Its authoring-plus-print step took about 12 seconds in the development environment; this is not a production performance claim. The prior dependency deployment succeeded, but this new request-lifecycle checkpoint must be published and exercised on the live site before the live timeout can be called resolved.
